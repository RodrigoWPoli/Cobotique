# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this repository is

A cobot project built on the teaching material of a workshop called "IA et Cobotique" (AI and collaborative robotics), held at Telecom Nancy. The workshop covers controlling a Universal Robots **UR5** arm through the **URSim** simulator from Python.

**Project goal: make the robot follow an object.** `project/follow_object.py` does this (see below; every command, option and parameter is in the root `README.md`). Reusable code goes in the `cobot` package (`src/cobot/`, installed editable by `uv sync`): `robot.py` (`Robot`, checked `move_j`/`move_l`/`gripper`), `kinematics.py` (UR5e DH FK), `vision.py` (camera, HSV detection, MobileNet-SSD, loading `MobileNetSSD_deploy.prototxt`/`.caffemodel` from the repo root), `calibration.py` (board ordering, homography, `pixel_to_robot`). Per-setup calibration values are in `config/calibration.json`; generated calibration data goes in `data/` (git-ignored). `README.md` has the setup steps, the project's commands and parameters, and the package usage.

**Workshop material is not tracked.** The decks, all Day notebooks (`workshop/notebooks/` holds the Day 1–2 versions that were tracked in `notebooks/` on master; `workshop/` itself holds the older copies plus Day 3–5), `tools/`, `image.png` and `trajectory.csv` live in **`workshop/`**, which is git-ignored and kept only locally. Paths in the workshop notes below are relative to `workshop/`.

Tests: `uv run pytest` (pure functions, no URSim needed except the `ursim`-marked test; `-m "not ursim"` to skip it). Git: the main branch is `master`; notebook outputs are stripped on commit by nbstripout and `*.pptx`/`*.caffemodel` go through Git LFS (both set up per clone by `scripts/setup_git.sh`). The caffemodel is not committed: `scripts/download_models.sh` fetches it with a checksum.

Each day has a French lecture deck `AI-and-Cobotics-Workshop-JourN_with_Gamma.pptx` and an English student notebook `DayN_*_Student.ipynb`, plus an optional instructor `DayN_*_Solution.ipynb`. The decks are 15–23 MB, so extract their text with `zipfile` (the `ppt/slides/slideN.xml` entries) rather than reading them directly.
- **Day 1, URSim setup** (16 Nov): AI paradigms, the perception → planning → action loop, UR5 kinematics, URSim, RTDE/URScript. The notebook covers connecting with `ur_rtde`, `moveJ`, `safe_move`, and logging the TCP pose to `trajectory.csv` (Polars + matplotlib).
- **Day 2, computer vision** (17 Nov). Exercises 1–4 are the user's original code, kept on purpose: capture, edges/contours, MobileNet-SSD, and a naive scale + offset `pixel_to_robot()`. Their `cv2.imshow`/`waitKey(0)` behaviour stays too. There are only 4 exercises, as in the original. Everything else lives inside the Final Challenge (the original Challenge text, verbatim), as steps that follow its list: steps 1–2 the HSV colour pipeline, step 3a checkerboard calibration, step 3b a homography `pixel_to_robot()` that replaces Exercise 4's, step 4 the pick in URSim. Students only run Exercises 1–4; only the step 4 pick cell carries `# Student Task`. Keep the original heading emojis (🎯 🧩 🎓) and don't add new ones. It uses webcam `/dev/video0`. Calibration uses the robot coordinates of three measured board corners (A, B, C), and `find_board()` re-orders the detected corners so that A is always the image's top-left corner. Don't simplify this to origin + angle: the detector can start from either end of the board, and a downward-looking camera mirrors the table, so a wrong orientation still fits with near-zero reprojection error but sends the robot 40 cm off. `Day2_ComputerVision_Student.original.ipynb` is the user's pre-rewrite version. There is no Day 2 solution notebook (the user deleted it; the last version is in git commit `442dfe2`). At the user's request, the student notebook's Challenge holds a deliberately lazy student answer: it reuses `snapshot.jpg` instead of a fresh frame, ignores every return value and always returns `True`. Don't "fix" it unless asked. `tools/check_day2.py <notebook> [--rotate90]` runs a Day 2 notebook end to end with a synthetic camera against URSim and checks the robot moves against ground truth.
- **Day 3** (announced in the Day 2 deck): path planning with A* and RRT, decision logic, an autonomous pick-and-place workflow.

- **Project: `project/follow_object.py`** (started 17 Nov). The UR5 follows a coloured object (HSV) seen by an **eye-in-hand** camera, using image-based visual servoing: P control on the image offset plus feedforward of the estimated object velocity, streamed with `servoL` at 50 Hz, at a fixed height and orientation, with the target clamped to `WORKSPACE`. In URSim a real webcam doesn't move with the robot, so the loop is open there. `--sim` renders a virtual tool camera from the actual TCP pose so the loop really closes. `--sim --headless --duration 25` is the self-test and prints the ground-truth tracking error (≈10 mm mean on the default Lissajous path). `--webcam-table` uses the PC webcam with URSim: the mirrored webcam frame is laid on the virtual table, 1.8× larger than the tool camera's view, and the tool camera sees the part under the TCP. `--no-robot` runs the detector on the webcam only. **Real robot:** an Intel RealSense D435i is mounted on the tool. Open it with `--camera realsense`, which globs `/dev/v4l/by-id/*RealSense*-video-index0` (the colour stream; currently `/dev/video6`, `video4` is infrared). The by-id name includes the serial `143523061441` only when the camera reports it: after a replug over USB 2 it didn't. The camera hangs on a VIA USB 3 hub/extension; it once failed to enumerate (`error -71`) after a replug, though it works on another machine. The script refuses a non-local `--ip` unless `--start-here` is given. That mode keeps the start orientation and servos in the plane of the start pose's tool X/Y (`Follower(A, origin)`, plane coordinates clamped to ±`--radius`), so a forward-looking camera moves sideways and up/down. If the camera doesn't look down, `--calibrate` is required. The forward case was tested with a wall-scene `SimCamera` subclass at the real robot's joint pose: 3.6 mm mean error. **Real robot:** a UR5e at `100.65.63.93` (PolyScope 5.11, Remote Control on), reached through the USB-Ethernet adapter at `100.65.63.101/16`. That subnet is inside Tailscale's `100.64.0.0/10`, whose firewall drops the replies, so `sudo tailscale down` is needed while using the robot. As of 17 Nov the camera looks forward (the tool is horizontal along −Y), and the red door in the lab triggers `red`. `--calibrate` measures the image Jacobian with ±5 cm moves (`--calib-step`) while the object stays still, so `CAM_YAW_DEG`/`CAM_FLIP` don't need to be known. Each position is the median of 20 frames, and the drift and +/− symmetry checks reject an object that moved. It saves to `data/follow_calibration.json`; `--load-calib` reuses it re-expressed in **tool** axes (`M_tool = J @ plane_cal.T @ R_cal[:, :2]`), so it stays valid when the tool is rolled. It only warns beyond 30° of view change. An earlier base-frame version would have reversed every direction after the 180° roll. `--set-home` saves the current position with the orientation snapped to the base axes (`square_orientation`), plus IK joints, to `data/follow_home.json`, without moving. `--home` does a slow `moveJ` there (refused above 45° on any joint) and then behaves like `--start-here`. Lab robot home: (0.148, −0.749, 0.540) m, rotvec (0, 2.2214, −2.2214), i.e. camera along −Y and tool X/Y = −X/−Z, wrist 3 ≈ −180°. That's the image the right way up; the first home, rotvec (π/2, 0, 0), showed it upside down. The `--start-here` box (default ±0.25 m) is shrunk by `reachable_box()`, which walks outward and rejects poses below `--min-z` (default 0.10 m), outside `isPoseWithinSafetyLimits`, without IK, or needing a joint change over 90°. **Don't pace the control loop with `rtde_c.initPeriod()`/`waitPeriod()`:** they wait for the RTDE interface's own period (2 ms at 500 Hz), not `DT`. Until 18 Nov that made the loop run at ~130 Hz and every speed 2–3× `--max-speed`; the loop now uses `perf_counter` pacing and integrates with the measured dt. `--follow-depth` adds tool Z as a third motion axis with `DepthFollower` (filtered depth at the object, jump rejection, deadband, brake without depth); `reachable_box` checks all axes (8 corners in 3D). **Call `getInverseKinematicsHasSolution` before `getInverseKinematics`:** asking `getInverseKinematics` for an unreachable pose stops the robot's control script (verified in URSim). `--calibrate-scene` needs no object: it measures the scene's median ORB displacement (it ignores matches that don't move, i.e. the tool in view). That fixes the directions exactly, and the scale is f/`--object-distance`. It exists because the user has nowhere to rest the object. The 5 cm step exists because, on 17 Nov, a hand-held object's jitter (≈24 px) matched the 22 px shift of the old 2 cm step, and the robot didn't follow properly. It was tested in `--sim` with `--sim-mount YAW FLIP` set to mountings the controller doesn't assume. The teach pendant's blue-green body triggers both the blue and green ranges, and the cream table triggers yellow and green, so use red or blue objects with the pendant out of view. The script starts with a `moveJ` to an elbow-up IK solution near `HOME_SEED_DEG`, because a `moveL` from an odd pose once left wrist 1 at −361° and triggered a protective stop. `CAM_YAW_DEG` / `CAM_FLIP` describe how the camera is mounted on the real tool.

## Conventions

- **Student notebooks contain deliberate `# Student Task` / `TODO` stubs.** Exercise 4 and the Challenge are meant to be left for students to complete. Don't fill them in unless asked; put a solution in a separate notebook (e.g. `*_Solution.ipynb`).

- Edit `.ipynb` files with the NotebookEdit tool, not as raw JSON.

## Running the notebooks

The robot notebooks need a running URSim instance (standalone or in a VirtualBox VM with a host-only adapter), set to **Remote Control** mode in Polyscope. The default target is `ROBOT_IP = '127.0.0.1'`.

The environment is managed with **uv** (`pyproject.toml`, `uv.lock`, `.venv/`). Python is pinned to **3.12** (`requires-python = ">=3.12,<3.13"`) because `ur_rtde` 1.6.5 only publishes wheels up to cp312. A newer Python would need a source build against Boost.

```bash
uv sync                                   # create/refresh .venv
uv run jupyter lab                        # or select the "Python (cobotique)" kernel in VS Code
uv add <pkg>                              # add a dependency
uv run jupyter nbconvert --to notebook --execute workshop/notebooks/Day1_URSim_Setup_Student.ipynb --output /tmp/out.ipynb   # headless run
```

`ur_rtde` provides the `rtde_control` and `rtde_receive` modules. **OpenCV is pinned `<5`** because OpenCV 5 removed `cv2.dnn.readNetFromCaffe`, which Day 2 Exercise 3 uses. The `MobileNetSSD_deploy.{prototxt,caffemodel}` files in the repo root (copies in `workshop/`) are chuanqi305/MobileNet-SSD's `deploy.prototxt` and `mobilenet_iter_73000.caffemodel`, renamed. Day 2 uses `cv2.imshow` windows (Qt5 build, runs through XWayland), so those cells need a desktop session and block until a key is pressed in the window. A Jupyter kernel named `cobotique` is registered in the user's kernelspecs and points at `.venv`.

### URSim (Docker)

URSim runs from `compose.yaml` using the official `universalrobots/ursim_e-series` image (pinned to `5.26` by digest, i.e. URSim 5.26.3) with `ROBOT_MODEL=UR5`. That is Polyscope 5.x, so the robot is really a UR5e. The e-series was chosen because the notebook relies on Remote Control mode, which only exists there. Ports are bound to localhost only; `ursim/programs` and `ursim/urcaps` are mounted volumes.

```bash
ursim/bringup.sh        # docker compose up -d + power on + brake release (idempotent)
docker compose down     # stop
```

- GUI: http://localhost:6080/vnc.html. **Remote Control** must be on, or `RTDEControlInterface` fails with `Failed to start RTDE data synchronization`. The "enabled" setting lives in `/ursim/.polyscope/remotecontrol.properties`, which is bind-mounted read-only from `ursim/polyscope/`. With it, a freshly created container accepts `RTDEControlInterface` right after `bringup.sh`, with no clicks in the GUI (verified 2026-11-16). Polyscope settings are in `/ursim/.polyscope/`; controller config and joint limits are in `/ursim/.urcontrol/` (`urcontrol.conf`, `safety.conf` → `*.UR5`).
- On URSim, the dashboard's `is in remote control` reply reads `false` even when remote control works, so don't use it as a check.
- Only **one** `RTDEControlInterface` can be connected at a time. A second one fails with `One of the RTDE input registers are already in use!`, which usually means a notebook kernel still holds the connection; call `rtde_c.stopScript()` or restart the kernel. Any number of `RTDEReceiveInterface` clients can connect.

- **`ur_rtde` 1.6.5 + Polyscope 5.26: `rtde_c.getForwardKinematics(q)` returns wrong poses for an explicit `q`.** Called with no arguments, it is correct (current pose). Use `cobot.forward_kinematics` (UR5e DH parameters) instead; `tests/test_kinematics.py::test_matches_ursim` checks it against `getActualTCPPose()` on the live controller.

UR ports the material refers to: 30001–30004 for URScript and dashboard traffic, 30002 for the secondary client interface, 30004 for RTDE. The code cells cannot run without a reachable URSim: the `RTDEControlInterface` constructor fails immediately if none is found.
